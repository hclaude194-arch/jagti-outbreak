# Jagti Outbreak: notes for Claude

Unity 6 (6000.0 LTS) URP project. The owner tests it in Unity on a laptop with Intel Iris Xe graphics, 16 GB RAM. Unity is not available in the cloud container, so nothing can be run there (a type check is possible, see below). Keep C# conservative, and say plainly in PRs that code is untested until the owner presses Play.

- Layout source of truth: `tools/layout/generate_layout.py` → `Assets/Data/campus_layout.json`. Map units are about 1 m. The origin is the central roundabout (map 414, 996), and map up is +Z. After editing, bump `VERSION` (Unity rebuilds the scene when it rises), then run `generate_layout.py` and `generate_terrain.py` in that order.
- Terrain: `tools/layout/generate_terrain.py` (numpy) writes the heightmap, splat, grass and tree data; `--preview` draws a top-down check image into `tools/layout/preview/` (gitignored). Its foothill-ridge shape is a design, not survey data; the owner asked for strong relief (flat terrain was rejected twice). The mess area sits on a terrace about 12 m above the girls' hostels and the faculty residences a little higher (`TERRACE_PADS`, owner's instruction); the mess terrace ends at a stone retaining wall beside the spine road (`RETAINING_X`, placed by `retaining_walls()` in build_outdoor.py), so move the two together. `tools/blender/render_terrain_views.py [view names]` renders eye-level checks of the terrain into `tools/blender/preview/`.
- C# type check without Unity: `apt-get install mono-mcs`, take UnityEngine.dll/UnityEditor.dll from the NuGet package `unity3d.sdk` 2021.1.14.1, stub URP and Unity.AI.Navigation types, and compile with `mcs`. This catches typos but not Unity 6-only API differences.
- The scene is generated by `Assets/Editor/CampusGreyboxBuilder.cs` (menu Jagti > Build Campus); do not hand-edit `Campus_Greybox.unity`. Textures and tree models are made from code into `Assets/Generated` (gitignored).
- Input: classic Input Manager (`UnityEngine.Input`), not the Input System package.
- Performance targets: 30 fps on Iris Xe, 0.8 render scale, baked lighting, fog-limited draw distance, zone streaming later.
- Blender works headless in the container through `pip install bpy` (Python 3.13; `import bpy` before `bmesh`). `tools/blender/build_buildings.py` builds the landmark FBX files from campus_layout.json (`--render` writes Cycles previews to `tools/blender/preview/`, gitignored). Git LFS uploads are blocked from the cloud container (lfs.github.com is denied), so the small generated FBX files are plain Git (see .gitattributes); keep them small. Material slot names must match `Assets/Editor/BuildingMaterials.cs`, and the tile sizes in both files must agree. Unity checks each model's bounds against building_models.json and corrects scale, turn or mirror.
- Building names come from the official campus plan. Treat names marked "?" on the vision map as guesses.
- Gameplay (Phase 3) lives in `Assets/Scripts/Gameplay/` (namespace Jagti.Gameplay); `Assets/Editor/GameplayBuilder.cs` wires it into the scene after the NavMesh bake. Zombies, view models and sounds are built in code at runtime (no prefabs or audio files yet). Each MonoBehaviour needs its own file named after the class.
- Interiors (Phase 4): `tools/blender/build_interiors.py` (run after `build_buildings.py`) writes the interior shell FBX, furniture FBX files in `Assets/Models/Props/` and `Assets/Data/interiors.json`; `Assets/Editor/InteriorBuilder.cs` places them before the NavMesh bake. Exterior doorways are cut in `build_buildings.py` (OUTER_DOORS, courtyard middle bays, BAY_DOOR_SEGMENTS, EAST_DOOR_Z); the interior walls copy the facade's window positions through `facade_openings`, so keep the two in step. Interior floors sit 0.6 m above each storey line. New material slots go in MATERIALS and `InteriorMaterials.cs`. Upper storeys: `level_openings` mirrors `academic_facade` floor by floor, and `hall_bays` (build_buildings) leaves the west facade open where the Mandapam hall covers it; change both sides together. Each level starts from the ground plan (`make_level`); furniture and lights carry a `level`, and `InteriorZone` draws only the camera's storey and its neighbours. Hostels and the mess (Phase 4C) are in `tools/blender/build_hostel_interiors.py`, imported by `build_interiors.py` (one shell and zone per building; props and lights carry `zone`, and zones carry `floorOffset`/`maxLevel`). Hostel rooms follow `hostel_facade` bay by bay (`facade_sides` replays it, and both take each window from `hostel_glass` and `HOSTEL_WIN_Z`), so change the two together; the hostel look (paired deep-set windows, jali stair cores between fins, solar roofs) is from the owner's photos and the satellite view, see project memory; hostel wings in the layout must touch, not overlap, so their corridors can be joined. The mess, shopping and medical interiors are drawn in world coordinates at their first spot (`INTERIOR_DESIGN` in build_buildings.py) and shifted to the layout's position, so the layout may move those buildings but must keep their sizes. Shops, the medical centre and the sports complex (Phase 4D) are in `tools/blender/build_civic_interiors.py` (plans written room by room in world coordinates); their shop fronts and doorways come from `SHOP_UNITS` and `CIVIC_DOORS` in `build_buildings.py`, which both files read.
- Outdoor props (Phase 4D): `tools/blender/build_outdoor.py` (run after the terrain and `build_buildings.py`) writes the street furniture FBX files and `Assets/Data/outdoor_props.json`; `Assets/Editor/OutdoorBuilder.cs` places them and sets sign text with TextMesh. Placement follows the layout (roads, paths, lawns, courts, places) and the terrain heightmap, so rerun it after layout or terrain changes.
- Battle royale (Phase 5, the default mode): runtime code in `Assets/Scripts/Royale/` (namespace Jagti.Royale); `Assets/Editor/RoyaleBuilder.cs` wires it in after the NavMesh bake. **Jagti > Game Mode** (EditorPrefs `Jagti.GameMode`) picks royale or zombie survival for the next build. Loot spots come from `tools/royale/build_loot_points.py` → `Assets/Data/loot_points.json` (run after `build_interiors.py`; `--preview` draws `tools/royale/preview/`). It keeps loot off furniture using `tools/royale/prop_sizes.json`, which `tools/royale/measure_props.py` (bpy) rebuilds when props change. Gun, item and brand names are original; copy no names, characters, art, UI or items from existing battle royale games. Bots (5B): `HumanBody.cs` builds a skinned body with `MeshKit.cs`; `tools/royale/preview_bodies.py` is a numpy port of its build and poses for Blender previews, so change the two together. Difficulty, the think scheduler and the cover search are in `BotTuning.cs`. Guns and attachments (5C): models in `LootVisuals.cs` use one gun frame (barrel +X, top +Z, thickness Y around Yc), with attachment mount points in `MountsFor`; `tools/royale/preview_guns.py` parses that C# to render them, so keep the call forms simple (P, Barrel, b.Box, b.Tube, b.Ball). Getting around (5D): `Vehicle.cs` (driving, damage) with models in `VehicleModels.cs`, `VehicleSpawner.cs` (parking spots found by RoyaleBuilder along roads and car parks), `ZipLine.cs` (sites found by RoyaleBuilder; `tools/royale/preview_getting_around.py` repeats the search on the heightmap) and `PlayerMover.cs` (vaulting, wading in the channels, riding, zipping). `tools/royale/preview_vehicles.py` translates the VehicleModels/ZipLine model code to Python to render it, so keep those to MeshKit calls, simple declarations, foreach over literal arrays and plain for loops. Map for battle (5E): cover models and placement come from `tools/royale/build_cover.py` (bpy; run after `build_outdoor.py` and `build_loot_points.py`) → `Assets/Models/Props/Cover_*.fbx` and `Assets/Data/cover_props.json` (outdoor_props format, placed by OutdoorBuilder in royale builds before the NavMesh bake); rerun it after layout, terrain or outdoor prop changes. `PropCuller` (Assets/Scripts/World) hides outdoor props past per-prop distances set in OutdoorBuilder. Online (5F): `Assets/Scripts/Net` (namespace Jagti.Net, plain C# with no Unity types: `NetPeer` UDP transport, `NetBuffer`) is tested by `tools/net/net_test.cs` with mono (see its header); `Assets/Scripts/Royale/Online` has `NetSession` (DontDestroyOnLoad connection and lobby), `NetLobbyMenu` (front menu; MatchDirector waits for it), `NetMatch` (in-match messages, types in `NetMsg`) and `NetPuppet`. Rules to keep: every machine runs the match from the host's seed, so `LootDirector.SpawnAll`, `PlanFlight` (the first use of MatchDirector's rng), haze centres and `SupplyDrop.Land` must stay deterministic; `Combatant.owned` decides who applies a hit (host owns bots, each player owns themselves; `ReceiveHit` forwards hits on others), so new damage goes through `ReceiveHit`; new loot changes go through `LootDirector.Add/Remove/SetCount`; new throws through `Grenade.Launch`; shots through `Ballistics.Fire`. Online the pause menu doesn't stop time (check `Time.timeScale == 0f`, not just `GameState.Paused`, before freezing match logic).
- HUD and menus (Phase 6A): IMGUI drawn through `Assets/Scripts/Royale/Ui/HudKit.cs` in reference units of a 1080-high screen (palette, generated textures, widgets; draws only on repaint, `useGUILayout = false`). `RoyaleHud` is a partial class: `RoyaleHud.cs` (state, compass, kill feed), `.Combat.cs` (player card, hotbar, ammo, crosshair, drop), `.Maps.cs` (minimap, haze timer, full map), `.Menus.cs` (pause, results); `NetLobbyMenu` is the front menu and shares `MenuPanels` (settings, controls). Settings live in `GameSettings` (PlayerPrefs). Icons are shape strings in `HudIcons.cs`; fonts are Barlow Condensed (OFL) in `Assets/Resources/Fonts` (plain Git, see .gitattributes). `tools/royale/preview_hud.py BACKGROUND.png [MAP.png]` mirrors the layouts with Pillow for mockups, so change the two together.
- Sky bus (Phase 6B): the drop craft is `SkyBus.cs` (flight, burner, sounds) with its model in `SkyBusModel.cs` (campus bus under a hot-air balloon, own 9-slot palette made in RoyaleBuilder). `tools/royale/preview_skybus.py` renders it through the preview_vehicles.py translator, so keep the model code in the same simple forms.
- Loot stashes and rich pickings (Phase 6C): `build_loot_points.py` also writes `stashes` (trunk spots against room walls from `STASH_ROOMS`, a few outside buildings; own rng stream so loot points don't move). `LootDirector.SpawnAll` picks two rich-pickings places (fuller, better floor loot), then fills stashes with sealed items (`LootStash`, `LootDrop.Sealed`) that open with E (`NetMsg.Stash` online). The trunk model is `StashModel.cs`, rendered by `tools/royale/preview_stash.py` through the preview_vehicles.py translator.
